Recommendation & Discovery,
as they actually run.

SlateClub surfaces films three different ways: a personalised feed, an essence-matched “films like this”, and an editorial browse page. Only the first two are intelligent — and neither uses a trained model. Nothing anywhere uses Reddit.

Live — real data, runs on request Inert — built, never trained or wired Absent — placeholder or no code

The two engines

Left is personalised and runs the four-stage pipeline. Right is seed-based, skips the pipeline entirely, and asks the LLM to reason about feel. They share almost nothing but the OpenAI layer.

POST /api/taste-engine/similar

Essence match — “films like Uncut Gems”

One seed film → the same felt journey. services/similar_films.py

1Cache check

In-memory, then the persisted SimilarCache table (versioned, keyed by tmdb_id). A hit skips the LLM entirely — most requests never reach step 2.

2Build the essence prompt

The seed’s emotional fingerprint, which the prompt says to weigh “far more than the plot”:

3One OpenAI call

Returns a one-sentence essence plus ~30 films picked purely by feel, each with a ≤6-word reason, spread across world industries. Uncut Gems is literally the prompt’s own teaching example — paired with The Social Network to show that zero genre overlap can still share an essence.

4Ground & enrich

Every named title is resolved through TMDB search to a real film with a poster — the LLM names, TMDB grounds. A director/cast row is appended, and the payload is persisted so the next person asking skips the LLM.

ALTFallback, no API key

Cosine over identity_embedding + affect_vector across the local catalog, after pulling TMDB’s own similar/recommended lists.

What the ranker actually weighs

The 12-feature fallback sum standing in for the untrained XGBoost model. The LLM’s semantic read of your taste outweighs every metadata signal — genre overlap counts for a twentieth.

Discovery — the browse surface

A different class of thing entirely: routes/discover.py is four thin aggregators, not an engine. Its own header calls it “Phase 1.5”. Two endpoints return real data; two are placeholders wearing a personalised costume.

Trending

GET /api/discover/trending

Genuinely real. Two editorial lists of recent releases across the five industries (Hollywood / Bollywood / Kollywood / Tollywood / Mollywood), sourced from TMDB via services/trending.py: recently in theatres and newly on OTT, with OTT films excluded from the theatrical list so each film shows its current state.

Artists radar

GET /api/discover/artists-radar

Circular artist tiles built from the favourite people you picked in onboarding (FavoritePerson, capped at 8). Real, though its docstring promises “plus a few high-popularity directors as filler” that the code never actually adds.

By platform

GET /api/discover/by-platform

Placeholder. Shows a per-platform “for you” count that is not personalised at all — it’s max(20, popular_count // (i + 3)), the same arithmetic for every user. Platforms are a hardcoded list of six. The docstring is candid: real counts wait on streaming_providers landing on Movie.

Awards

GET /api/discover/awards

Static. Returns six hardcoded labels — Oscars 2025, National Film Awards, Cannes, Venice, Berlinale, Sundance. No films, no lookup, no database. A constant in the file.

Where the intelligence lives

Discovery’s own docstring says the “heavy lifting lives in the recommendation pipeline / taste graph and is reused here” — but in practice these four endpoints reuse none of it. The personalised surfaces are /for-you and /taste-engine/similar.

Reddit / Letterboxd

Not implemented anywhere — no praw, no credentials, no hook. Proposed in backend/docs/recommendation-improvements.md to enrich movie identities with real audience reaction. The “existing stub” those docs cite isn’t in the code.

The shared substrate

OpenAI layer

  • gpt-5.5 — essence reasoning, taste statements, identity extraction
  • text-embedding-3-large — 3072-dim, packed to bytes
  • Offline job writes identity_json + identity_embedding — never on the request path
  • No key → semantic paths degrade to cosine

Taste graph — Neo4j

  • WATCHED 0.6 · RATED rating/5 · REVIEWED 1+sentiment
  • TASTE_SIMILAR written only at ≥0.7 cosine
  • Louvain → Cinematic Tribes (resolution 1.0, min 2)
  • Feeds cluster consensus + friend boost

Services

  • taste_cache — Redis, 15-min TTL
  • taste_embedding — builds UserTasteState
  • watch_signals — graph + bandit + similarity hub
  • diary_service — keeps watch_log ↔ WatchHistory in sync

What recs read

  • WatchHistory — the watched set used
  • MicroFeedback — dismissals used
  • watch_log (per-viewing diary) — not read directly; reaches recs only via the summary upsert

Contextual bandit

  • 5 arms; rewards persist to bandit_state.json
  • Weights never reach the pipeline — exposed only at /api/taste/bandit/weights
  • discovery_seeker segment is unreachable

Training data, uncollected

  • Impression logs every card shown — surface, position, rank_score, source
  • Purpose-built as XGBoost negatives
  • Nothing consumes it yet. The highest-leverage unlock available

Drawn from a read of the live source, not the prior documentation — which still described the LLM layer as Gemini, the ranker as 11 features, and the taste blend as a fixed 0.7 / 0.3 split. All three were wrong. The recommendation engine is a well-architected hybrid currently running entirely on hand-tuned heuristics; the learned layer is scaffolding waiting on the impressions it is already collecting. Discovery is, for now, mostly a façade over TMDB. Companion to Recommendation.md.
